# Передача проекта из чата в чат: v1 -> v2

## Что это за проект

Сервис поиска поставщиков продуктов питания. Тестовое задание для Goulash.tech
(Екатеринбург, автоматизация доставки для ресторанов).

Пользователь выбирает категорию товара и город, сервис находит реальные
организации, показывает их контакты и балл «насколько поставщик готов к
контакту», чтобы было понятно, кому звонить первым. Данные живые, ничего не
выдумано, у каждой карточки есть ссылка на источник.

Версия v1 заморожена в github.com/zahar-pr/goulash-find (ветка `main`, один
коммит `init`), её трогать нельзя. v2 живёт отдельным репозиторием
github.com/zahar-pr/v2, ветка `main`; локально это папка `system v2`, remote
`origin` смотрит на v2, remote `v1` — на старый репозиторий.

## Стек и запуск

Python 3.12, FastAPI, aiohttp, SQLite (stdlib `sqlite3`, файл `data/provizia.db`).
Фронтенд — React 18 + Vite. Внешних зависимостей у бэкенда три: fastapi, uvicorn,
aiohttp.

    ./run.sh                     # соберёт frontend/dist и поднимет
                                 # http://127.0.0.1:8000
    cd frontend && npm run dev   # дев-режим на 5173, /api проксируется на 8000
    docker build -t goulash-find .

Переменные окружения: `DB_PATH` (где лежит база), `PROVIZIA_WORKERS=0`
(выключить фоновые задачи, нужно в тестах), `TWOGIS_KEY` (включает источник 2ГИС),
`ADMIN_TOKEN` (включает `/api/admin/*`), `PORT`.

## Как это работает

Раньше каждый поиск шёл в Overpass и занимал 4–15 секунд. Теперь между
пользователем и источниками стоит индекс в SQLite.

**Наполнение.** При старте `index.prewarm()` обходит 26 городов и для каждого
делает **один** запрос в Overpass сразу по всем тегам всех категорий (34 тега).
Город — 10–20 секунд, весь индекс — около 8 минут, всё в фоне. Результат
складывается в таблицу `suppliers`, город помечается в `refreshes`. Повторно
город обновляется через 7 дней (`REFRESH_TTL`).

**Выдача.** `GET /api/suppliers` не ходит в сеть вообще: фильтры, поиск,
сортировка и пагинация — это один SQL-запрос, ответ за единицы миллисекунд.
Исключение одно: если пользователь выбрал город, которого ещё нет в индексе,
запрос дожидается `ensure_city()` — те самые 10–20 секунд, один раз.

**Обогащение.** Вторая фоновая задача `enrich_forever()` берёт из индекса
поставщиков с сайтом и вытягивает то, чего в OSM нет: сайт разбирается
регулярками (`sources/website.py`), Wikidata сверяется по официальному сайту.
Оттуда берутся email, телефоны, ИНН и ОГРН, упоминания документов (ТР ТС, ХАССП,
ISO 22000, халяль, ветеринарные), минимальный заказ, цена, условия доставки,
география поставок, год основания и описание. Если контакт из OSM нашёлся на
сайте компании — карточка получает `verified` с пометкой, чем именно
подтверждена. После обогащения балл пересчитывается.

## Решения, принятые осознанно: не ломать и не «улучшать» вслепую

1. Источники подключаемые: класс с `collect()` плюс строка в `SOURCES`.
   `ready()` решает, включён ли источник, — 2ГИС сам себя выключает без ключа.
   Упавший источник не ломает индексацию города.
2. Один запрос в Overpass на город, а не на категорию: 34 тега в одном запросе
   отрабатывают за то же время, что раньше один. Категории раскладываются уже
   на нашей стороне (`catalog.categories_for`).
3. Область поиска — квадрат вокруг центра города: 14 км, для Москвы и
   Санкт-Петербурга 24 км. Полная рамка города давала те же организации втрое
   медленнее.
4. Три зеркала Overpass опрашиваются наперегонки, берётся первый ответ.
5. База — SQLite и ничего больше. Postgres здесь нечего делать: данных тысячи
   строк, запись только из фоновых задач, а один файл разворачивается где угодно.
6. Балл 0–100 — это готовность к контакту, а не качество продукции: телефон 25,
   сайт 15, email 15, опт или производство 15, документы 10, реквизиты 7,
   адрес 8, часы 5. Уровни: >=65 «Звонить первым», >=40 «Хороший кандидат»,
   ниже «Мало данных». В карточке видно, из чего балл сложился.
7. `rating` в интерфейсе — это «рейтинг данных», балл делённый на 20. Если
   источник даст настоящий рейтинг (2ГИС), он не затирается: `save_rating`
   обновляет поле, только пока `reviews` пустой.
8. Обобщённые теги OSM (`shop=wholesale`, `shop=trade`, `shop=houseware`)
   означают оптовика вообще, а не пищевого. Такие объекты берутся, только если
   в названии есть пищевой признак, иначе в выдачу лезут подшипники и генераторы.
9. Заметки привязаны к анонимному пользователю из httpOnly-cookie. Логина нет и
   не нужно: человек открыл сервис и сразу пишет заметки, они переживают
   перезагрузку и не видны другим.
10. `verified` не рисуется само: его ставит либо перекрёстная сверка с сайтом
    компании, либо менеджер через `/api/admin/verify` с `ADMIN_TOKEN`.
11. Разметку рисует React, экранирование на нём же: названия приходят из OSM и с
    чужих сайтов, их пишут посторонние люди.

## API

    GET  /api/meta                    категории, регионы, города по регионам,
                                      сортировки, дефолты, статистика, источники
    GET  /api/status                  статистика и прогресс фоновых задач
    GET  /api/suppliers               q, category, region, city, onlyDocs,
                                      onlyVerified, onlyWholesale, sort, page, perPage
                                      -> { items, total, page, pages, perPage, stats, status }
    GET  /api/suppliers/{id}          карточка целиком
    GET  /api/notes                   заметки текущего пользователя
    POST /api/notes                   { supplierId, text }, пустой текст удаляет
    DELETE /api/notes/{id}
    POST /api/compare/recommend       { ids: [...] } -> { bestId, cheapestId, text }
    POST /api/admin/verify            { supplierId, verified, token }
    POST /api/admin/refresh           { city, token } — переиндексировать город

## Что в интерфейсе действительно работает

Всё, что нарисовано, ходит в бэкенд и считается на нём:

- строка поиска — по названию, категории, виду, городу, адресу, документам и
  описанию; дебаунс 350 мс, поиск в SQL;
- чипсы категорий, «Все категории», регион, город (список городов зависит от
  региона), сортировки;
- чекбоксы «Только с документами», «Данные подтверждены», «Опт и производство» —
  все три фильтруют по реальным полям;
- пагинация «Показать ещё» по 12 карточек;
- панель поставщика: контакты, реквизиты, документы, условия, ссылки на все
  источники, дата проверки;
- заметки — сохраняются в SQLite автоматически, переживают перезагрузку;
- сравнение до трёх поставщиков, рекомендация считается на бэкенде;
- баннер прогресса, пока индекс наполняется.

## Честность данных

Ничего не выдумывается. Пустое поле показывается как «нет данных» — это значит,
что источник его не дал. Что реально наполняется:

- из OSM: название, вид, адрес, телефоны, email, сайт, часы, признак опта,
  координаты, ссылка на объект;
- с сайта поставщика: email и телефоны, ИНН и ОГРН, документы, минимальный заказ,
  цена, доставка, география, год основания, описание;
- из Wikidata: год основания и подтверждение, что сайт принадлежит компании;
- из 2ГИС (если задан `TWOGIS_KEY`): рейтинг, число отзывов, контакты.

Поля `manager` и настоящий рейтинг без ключа 2ГИС остаются пустыми — взять их
неоткуда.

Обогащение упирается в сайты: часть организаций сайта не имеет, часть сайтов
отвечает дольше таймаута, часть — SPA без текста в HTML, а у некоторых домен
давно перекуплен. Последнее отсекается проверкой `_relevant`: если на странице
нет ни имени компании, ни пищевых слов, данные не берутся. Неудачные попытки
повторяются до трёх раз (`enrich_tries`), потом поставщик остаётся с тем, что
дал OSM.

## Что было сделано и сознательно удалено при упрощении

Если понадобится вернуть — код лежит в истории v1 до коммита `init`: заметки и
свои поля по поставщику вместе с SQLite, шортлист, сравнение до 4 поставщиков,
выгрузка CSV, обогащение с сайтов поставщиков (email, ИНН, сертификаты,
минимальный заказ, доставка — парсер на регулярках), веб-поиск официальных
сайтов через DuckDuckGo, провайдеры 2ГИС и DaData, фильтр «только опт», поиск по
регионам, ссылки «проверить вручную» (Яндекс, 2ГИС, ЕГРЮЛ, Rusprofile).

## Известные ограничения

- Первый запуск: индекс пустой, наполняется около 8 минут. Интерфейс это
  показывает, выбор конкретного города индексирует его сразу.
- Overpass остаётся узким местом при обновлении: 10–20 секунд на город.
- В OSM у производств часто есть название и адрес, но нет телефона и сайта —
  отсюда низкие баллы.
- Документы находятся только у тех, кто написал о них на своём сайте.
  Реестров сертификатов с открытым API нет.
- `KIND_TITLES` надо держать в соответствии с тегами категорий, иначе в карточке
  появится сырой тег вместо подписи.
- Настоящих отзывов и рейтингов нет, пока не подключён 2ГИС с ключом.

## Требования к стилю — жёсткие

- Никаких комментариев и докстрингов в Python. Проверяется разбором AST:
  ноль штук.
- Файла README.md быть не должно, заново не создавать. Вся передача контекста —
  этот файл.
- Простота важнее функциональности, сложность проекта не наращивать.
- Python форматируется `black -l 99` и `isort --profile black`, проверки
  `--check` должны проходить молча.
- Интерфейс на русском, дизайн-система «Провизия»: светлая тема (фон #E7EDF0,
  карточки #F8FBFC, тёмный блок #0A3440), два акцента — циан #00E1E1 и мята
  #2BE2A0. Заголовки Yandex Sans Display, текст Onest. Палитра, скругления,
  анимации и брейкпоинты объявлены в `styles/global.css` и согласованы.
- Данные только живые. Правдоподобные значения не придумывать никогда.

## Куда расти дальше

- 2ГИС с ключом: рейтинг, отзывы и контакты почти по каждой организации РФ —
  код уже написан, включается переменной окружения.
- DaData или ЕГРЮЛ для реквизитов и статуса юрлица по ИНН, который уже находится
  на сайтах.
- Полноценная модерация: интерфейс менеджера поверх `/api/admin/verify`,
  очередь на проверку, история изменений.
- Запрос КП из карточки со статусом (отправлено / ответили / отказ).
- Аналитика выдачи: какие категории и регионы ищут чаще.
- Регионы целиком через `area` в Overpass вместо квадрата вокруг центра.

## Деплой

Площадка — **Render**, free-тариф: 512 МБ, 0.1 CPU, карта не нужна, сборка из
нашего Dockerfile. Hugging Face Spaces отпали: у них Docker и Gradio закрыты
замком «Paid», бесплатен только Static, а на статике бэкенда нет.

Ключевое решение: **индекс едет внутри образа**. `data/seed.db` — слепок рабочей
базы (чекпоинт WAL, заметки вычищены, VACUUM), он лежит в git, Dockerfile кладёт
его в `/app/seed`, а `docker-entrypoint.sh` на первом старте копирует в
`DB_PATH`, если базы ещё нет. Поэтому прогрева на 8 минут пользователь не видит.
Замерено на собранном образе: **1.1 секунды** до первого ответа API, поиск с
фильтрами — 9 мс, потребление 76 МБ памяти.

Конфигурация — `render.yaml` (blueprint): `runtime: docker`, `plan: free`,
регион `frankfurt`, ветка `main`, healthcheck на `/api/meta`. `PORT` Render
подставляет сам, энтрипоинт его читает.

Порядок публикации:

1. `git push origin main`
2. render.com -> Sign up with GitHub -> New -> Blueprint -> репозиторий
   `zahar-pr/v2`, ветка `main` -> Apply. Сборка около 5 минут.
3. В настройках GitHub-репозитория задать переменную `SITE_URL` =
   `https://provizia.onrender.com` (или тот адрес, что выдаст Render).

Свободный инстанс засыпает после 15 минут простоя и просыпается 30–60 секунд —
это лечит `.github/workflows/keepalive.yml`, который пингует `${SITE_URL}/api/meta`
каждые 10 минут. В месяц выходит около 730 инстанс-часов при лимите 750.

Обновление слепка перед деплоем: запустить сервис, дать ему добрать обогащение,
затем пересобрать `data/seed.db` (чекпоинт WAL, `DELETE FROM notes`, `VACUUM`) и
закоммитить.

Диск на бесплатном тарифе не постоянный: после перезапуска индекс вернётся из
образа мгновенно, а заметки пользователей пропадут — для демо-стенда это принято
сознательно. Нужна постоянность — платный диск Render или свой VPS.

Скорость отдачи: `GZipMiddleware` (бандл 167 КБ -> 53 КБ) и кэш статики —
`no-store` для index.html, `immutable` на год для хешированных `/assets/`,
неделя для шрифта и фавикона.
